# T2.4 — Stripe Billing: checkout, portal, webhooks, dunning

`[N]` · size **L** · **Status: done** (22 September 2026) · depends on T2.3

## Why

T2.3 made entitlements one canonical registry, but the money path was still a
stub: `billing.changePlan` let a signed-in user raise their own plan (it is off
by default, but it is not billing), `billing.cancelPlan` switched off instantly
with a `TODO (review G4)` about wind-down, and `PLANS` prices lived in the UI.
There was no checkout, no portal, no webhook, no dunning and no reconciliation.

> **Reference docs:** the T2.4 row in `docs/pack/10-build-backlog.md` cites
> `docs/pack/04-adrs.md` (ADR-5), which — like in T2.1/T2.2/T2.3 — is **not
> present in this working tree**. T2.4 was scoped from the self-contained backlog
> row (*"Products per add-on; verified idempotent webhooks; reconciliation job;
> `past_due` → `wind_down` policy; MOSAI's own tax setup"*, acceptance
> *"Duplicate and out-of-order webhooks change nothing twice; entitlement drift
> 0"*) plus `AGENTS.md` §5 rules 5/6/7 and §6. The Stripe seam below is the one
> place to re-point if ADR-5 lands differently.

## Do — what was built

### 1. Schema (additive)

`users.planStatus` gains `wind_down`; `users.isPlatformAdmin` is added. New
tables: `platformAdmins`, `adminAuditLog`, `billingCustomers`, `subscriptions`,
`billingEvents`, `billingReceipts`, `billingInvoices`, `reconciliationRuns`. All
are registered in `lib/dataRegistry.ts`.

### 2. The provider seam — `src/convex/lib/stripe.ts` (new)

A small REST client with the safety rules encoded in one file: **test mode only**
unless `STRIPE_LIVE_MODE=true`; **every POST requires an idempotency key**;
**webhook signatures are mandatory** (HMAC-SHA256 over `t.payload`, constant-time
compare, 300s replay tolerance) via Web Crypto. No feature code calls Stripe
directly.

### 3. Catalog — `src/convex/lib/billingCatalog.ts` (new)

Plan → price id is read from `process.env` (`STRIPE_PRICE_STARTER` /
`_GROWTH` / `_SCALE`), never hard-coded; plans come from the T2.3 registry (no
new tier list). Provider status → local mirror status mapping, and the
`metadata.mosai_organization` / `metadata.mosai_plan` keys the webhook resolves
by. A per-add-on price seam (`STRIPE_PRICE_ADDON_*`) is declared for the
future, unused today.

### 4. Functions — `billing.ts` + `billingWebhooks.ts` + `http.ts` + `crons.ts`

- `billing.currentOrganization` / `catalog` / `subscription` (read side, org-scoped).
- `billing.startCheckout` (org action) creates/reuses a Stripe customer and a
  subscription-mode Checkout Session; **it returns a URL and writes no plan**.
- `billing.openPortal` (org action) opens the billing portal.
- `POST /api/stripe/webhook` verifies the signature, then calls the internal
  `billingWebhooks.applyEvent`, which is the **only** writer of the local mirror:
  idempotent by event id, out-of-order-safe by `subscriptions.lastEventCreated`,
  and never grants entitlement from a checkout alone (a completed checkout is
  recorded as a receipt; `customer.subscription.*` owns entitlement).
- Dunning (`invoice.payment_failed` advances the stage, sets `windDownAt`),
  `past_due` → `wind_down` sweep, and a daily reconciliation job
  (`billing.reconcileNow`) over the pure `lib/billingReconcile.ts`.

### 5. Platform admin panel (the paired request)

`julian.s.witkowski@gmail.com` is a platform operator through
`lib/platformAdmin.ts` (a deployment email allow-list, extensible with
`PLATFORM_ADMIN_EMAILS`, plus `users.isPlatformAdmin` and the legacy `admin`
role). `guards.requirePlatformAdmin` is the only entry point; `ads.copilot`'s
old `role === "admin"` check now uses it too. `/admin` (route in `main.tsx`,
link in `AppShell`) shows platform stats, Stripe configuration, the webhook
ledger, the reconciliation report, per-organization plan overrides (audited in
`adminAuditLog`) and operator grant/revoke. Every write is recorded.

## Acceptance criteria — proof

| Criterion | Proof |
|---|---|
| Duplicate webhooks change nothing twice | `tests/unit/billing.test.ts` → "a duplicate delivery changes nothing twice": second `applyEvent` returns `{duplicate: true}`, one subscription row, one ledger row. |
| Out-of-order webhooks change nothing | "an out-of-order delivery does not un-do a newer state": a late `canceled` event older than the applied `active` one is `ignored`, the mirror stays `active`. |
| A browser redirect alone never grants a plan | "a browser redirect (a completed checkout alone) never grants a plan": `checkout.session.completed` writes a receipt but the user stays `free` with no subscription. |
| Reconciliation reports 0 drift | "reports 0 drift when the mirror matches the provider" (`driftCount === 0`), and "names every disagreement when a plan drifts" (`plan_mismatch`, `mirror_mismatch`). |
| `past_due` → `wind_down` is honest | "keeps entitlement during the grace period, then moves to `wind_down`": `past_due` still entitled, then `wind_down` + `free`, the subscription row kept (nothing deleted). |
| Signature verification / test-mode guard | "verifies a webhook signature and rejects a stale or wrong one", "refuses a live key unless the owner opted in". |
| Admin panel exists and the listed email has access | "grants the bootstrap operator by email, and the panel refuses everyone else", "lets an operator override a plan and records the action", "grants and revokes operator access, and refuses self-revocation". |

### Defect found and fixed (regression test)

An `invoice.*` event can arrive **before** its `customer.subscription.*` mirror
exists. `syncEntitlement` then found no governing subscription and silently
downgraded the customer to `free` — a paying customer losing access because two
deliveries raced. Fixed in `billingWebhooks.handleInvoice`: an invoice whose
subscription is not yet mirrored is `ignored` (its subscription event owns
entitlement). Regression: "an invoice that arrives before its subscription is
ignored (regression)".

### Test-infra defect found in final verification (fixed)

The first cold, 2-worker run of this session failed the a11y gate with one
serious `color-contrast` node on `/auth` — and was unreproducible afterwards
(18+ warm runs clean). The cause is a race, not a product contrast bug: axe
samples rendered colours while the card's 0.55s `mosaic-in` entrance fade (and
the web-font swap) is still in flight. `tests/e2e/a11y.spec.ts` now calls a
`settleForAxe` helper (waits for `document.fonts.ready` and for every finite
`mosaic-in`/`mosaic-pop` animation to finish; the infinite decorative
`mosaic-float` loops are excluded) before analysing, and on failure logs the
offending nodes so CI output is diagnosable. The assertion itself is unchanged:
zero serious/critical violations, no allow-list.

## Security and privacy notes

- No plan state is written by a client-callable mutation from a browser
  redirect; `active`/`trialing`/`paid` come only from verified webhook code
  holding a provider record.
- Money is integer minor units + currency; receipts are stored for every write
  that claims money moved.
- Operator access is server-resolved and audited; a client can never grant it.
- No key value is ever returned by an admin query (booleans only).
