# T2.17 — Tool calling in `ModelGateway`

`[N][R]` · size **M** · **Status: code done, proof outstanding** (24 September 2026) · depends on T2.9 (the gateway exists)

## Why

The owner accepted option C in `docs/decisions/2026-09-24-in-product-ai-agent.md`: a native MOSAI copilot that can read the whole project, point the user to the right step and prepare drafts. Before this ticket, `ModelGateway` could only do single-shot text completion, with no tool-call request or response shape. Every AI feature carried the line "No tools are available". A copilot needs the model to *ask* for typed MOSAI functions, and it needs server code to decide whether each ask runs.

## Scope

In scope:

- `modelToolStep` in `src/convex/lib/modelGateway.ts`. It sends one OpenRouter request with `tools` and `tool_choice: "auto"`, normalizes the reply into text plus tool calls, and records one `aiRuns` row. It never executes a tool.
- `runAgentLoop` and `defineAgentTool` in `src/convex/lib/agentLoop.ts`. The loop is bounded, validates every call, and executes tools.

Out of scope (later tickets):

- The actual MOSAI tools (T2.18).
- Threads, the dock UI and the per-turn quota (T2.19).
- Budgets per plan (owner decision 3, still open).

## Rules the code enforces

| Rule | Where | Test (`tests/unit/agent-loop.test.ts`) |
|---|---|---|
| Only tools the caller registered exist, and the offered list never changes inside a turn | `runCall` refuses unknown names with `unknown_tool` | "refuses a tool the caller did not register, even when tool output asked for it" |
| Arguments are parsed and schema-validated before a handler runs; rejected values are not echoed back | `defineAgentTool().parse` (zod) | "never runs a handler on invalid arguments…" |
| Effects are limited to `read`, `navigate` and `draft`: nothing that publishes, sends or spends (AGENTS.md rule 5) | `defineAgentTool` | "refuses tools that take tenant ids from the model or have an outside-world effect" |
| Tenant ids (`projectId`, `userId`, `organizationId`, `ownerId`) are never model arguments; handlers close over server-resolved context (rules 2 to 4) | `defineAgentTool` | same |
| Hard step cap (`AGENT_LOOP_MAX_STEPS = 6`); pending calls at the cap are answered, not run, so the thread stays well-formed | `runAgentLoop` | "stops at the hard step cap…" |
| At most `MODEL_GATEWAY_MAX_TOOL_CALLS_PER_STEP = 8` calls per step; beyond that the run fails as `invalid_output` | `modelToolStep` | "fails the run when one step asks for more calls…" |
| One `aiRuns` row per step, with fixed error categories only | `modelToolStep` | "runs a validated call…", "rejects an invalid tool request…", "records an empty reply…" |
| Handler errors reach the model only as `tool_failed`; only `AgentToolError` messages pass through | `runCall` | "reports handler failures by category…" |
| Malformed provider tool calls are dropped before they reach a handler | `normalizeToolCalls` | "drops malformed provider tool calls…" |
| Navigation and other UI come from structured tool output (`outcomes[].result`), never from the model's prose | `AgentLoopResult.outcomes` | "runs a validated call…" |

## Before / after

- **Before:** `modelComplete` only, text in and text out; the OpenRouter body had no `tools`.
- **After:** `modelComplete` is unchanged for all existing features (every existing gateway test passes, with `toolCalls: []` added to the normalized shape). The new `modelToolStep` and `runAgentLoop` are not yet called by any feature.

## Data migration

None. `aiRuns` is unchanged. Tool steps record `provider: "openrouter"` and the caller's `agentId`.
