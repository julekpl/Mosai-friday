# T2.2 — Org-scoped function builders and generated cross-tenant tests

`[R][N]` · size **L** · **Status: done** (22 September 2026) · depends on T2.1

## Why

T2.1 made the organization the tenant but left every project function comparing
`project.ownerId !== userId` inline — 81 occurrences, per the authorization audit.
That rule cannot express a teammate: a project moved under an organization was
reachable only by its creator, so the organization existed in the schema and
nowhere in the authorization path. Worse, the inline pattern is fragile in the
dangerous direction too: one forgotten line is a cross-tenant read or write (that
is exactly how the `collections.create` bug shipped).

T2.2 moves tenancy into **one reviewed place** — the builders and helpers in
`guards.ts` — and adds the two gates that keep it there: a lint ban on raw
`ctx.db` project lookups outside the data-access layer, and a generated suite
that exercises every public function with a foreign-organization caller.

> **Reference docs:** the T2.2 row in `docs/pack/10-build-backlog.md` and the
> ADR-2 section it cites live in `docs/pack/08-module-contracts.md` / `04-adrs.md`,
> which are **not present in this working tree** (same gap T2.1 recorded). T2.2
> was scoped from the self-contained backlog row plus `AGENTS.md` §5 rules 2/10/12
> and §6. The builder signatures and the `OrgAccess` shape are therefore the only
> new contract; they are the one seam to re-point if ADR-2 lands differently.

## Do — what was built

### 1. Org-scoped builders (`src/convex/guards.ts`)

- `OrgAccess` — the authorized context every handler receives: `userId`,
  `organizationIds`, `requireUser()`, `requireProject(id)`, `ownedProject(id)`,
  `ownedRow(row)`, `requireOrganization(id)`.
- `orgQuery` / `orgMutation` wrap Convex's `query` / `mutation` and resolve the
  caller's **active organization memberships** once, per call.
- `orgAction` does the same for actions, through internal probes (actions have no
  `ctx.db`): `guards.isAnonymousUser`, `guards.activeOrganizationIds`,
  `guards.projectAccessForAction`, `guards.organizationAccessForAction`.
- One tenancy rule, `hasProjectAccess`: the caller must be an **active member of
  the organization that owns the project**; a row that predates T2.1's migration
  and has no `organizationId` still falls back to its owner, so the migration and
  the authorization path cannot disagree mid-rollout.
- `requireProject` / `ownedRow` / `projectForRead` now use that rule; `assertModule`
  is still the plan check and is still explicitly **not** ownership.
- Node-only action files (`buildChat.ts`, `sellAI.ts`) authorize through
  `internal.guards.projectAccessForAction` rather than importing the builder
  module, which cannot be defined in a `"use node"` file.

### 2. Migration of the 81 inline checks

All 81 `project.ownerId !== userId` checks are gone — **27 convex modules** now go
through the builders or the shared helpers: `ads/control`, `ads/copilot`,
`ads/oauth`, `ads/sync`, `buildPages`, `buildWorkspace`, `builds`, `campaigns`,
`cms`, `collections`, `communications`, `contacts`, `content`, `contentPlanning`,
`files`, `insights`, `journeys`, `personaChat`, `personas`, `posts`, `products`,
`projects`, `sell/queries`, `shopifySync`, `social/copilot`, `social/executor`,
`social/oauth` (plus the action and internal-helper call sites in `buildChat`,
`buildInternals`, `sellAI`, `storefront`).

`projects.list` also stopped being owner-scoped: it now returns every project
owned by one of the caller's active organizations (plus legacy owner-only rows),
which is what makes "a client of another organization can reach the projects they
are members of" true in the product, not just in the guard.

### 3. Lint ban on raw `ctx.db`

`eslint.config.js` adds `no-restricted-syntax` for `src/convex/**/*.ts`: a bare
`ctx.db.get(projectId)` and a bare `ctx.db.query("projects")` are **errors**,
with the data-access layer (`guards.ts`, `dal.ts`, `organizations.ts`,
`projects.ts`, `billing.ts`, `lib/**`, `_generated/**`) as the explicit ignore
list — those files *are* the layer. Feature code must use `access.requireProject()`
/ `access.ownedProject()` / `access.ownedRow()`, or `guards.projectAccessFor()` /
`projectForRead()` from a helper.

### 4. Generated cross-tenant suite

- `tests/unit/function-registry.ts` — the generator. `import.meta.glob` loads
  every module under `src/convex/**` the way the test backend does, keeps the
  `isPublic` functions, and reads each one's argument schema from Convex's own
  `exportArgs()`. Nothing is hand-listed: a new public function enters the
  registry the moment it is written, and `tenantScoped` is `true` exactly when an
  argument names a record (`v.id(...)`, including nested objects and unions).
- `tests/unit/cross-tenant.fixtures.ts` — seeds tenant Alice with a real user,
  project and organization, then materializes one **real** row per table an
  argument references, so the foreign caller is handed Alice's real ids rather
  than fabricated ones; it records any table it had to fake so the suite can
  assert that it did not.
- `tests/unit/cross-tenant.generated.test.ts` — 163 generated cases (one per
  record-scoped public function) plus 2 structural ones. Each generated case
  proves the caller really is foreign (Bob is a real customer of his **own**
  organization, and his org set is disjoint from Alice's), then calls the
  function as Bob with Alice's ids and asserts **nothing was written** (per-table
  row counts identical) and **nothing was revealed** (null / empty array / empty
  object).

## Acceptance — evidence

### Acceptance criterion 1 — CI fails on an unscoped public function

`scripts/audit-public-functions.mjs` (run by `bun run check` and the CI
`security` job) now recognizes the org builders and fails on all three unscoped
shapes:

| Shape | Result |
|---|---|
| no sign-in check at all | **FAIL** |
| authenticates but names a record (`v.id(...)`) and never authorizes it | **FAIL** |
| authorizes inline with `project.ownerId !== userId` | **FAIL** (was a warning) |
| authenticates, names no record (self-scoped: own user row, upload URL, admin setting) | REVIEW (warning) |

`tests/unit/audit-gate.test.ts` (5 tests, `node` environment) runs that exact
script against throwaway convex modules, so the gate is proven to fire rather
than observed to pass: an unscoped query → exit 1, a no-auth query → exit 1, an
inline `ownerId` check → exit 1, an `orgQuery` read authorizing through the access
object → exit 0, and the real tree → exit 0.

**Audit before → after** (`bun run audit:functions`):

| | before T2.2 | after T2.2 |
|---|---|---|
| public functions scanned | 198 | 198 |
| authorize through a shared guard / org access helper | 106 | **191** |
| inline `ownerId` authorization | **81** | **0** |
| authenticate but never authorize (REVIEW) | 8 | 4 |
| unscoped / unauthenticated (FAIL) | 0 | 0 |
| exit code | 0 | 0 |

The 4 remaining REVIEW items are self-scoped and name no record:
`ads/copilot.setCopilotModel` (admin role check), `billing.currentPlan`,
`files.generateUploadUrl`, `users.currentUser`. `scripts/public-functions-allowlist.json`
is **unchanged — still exactly 3 entries** (the two OAuth callbacks and the public
published-CMS read).

### Acceptance criterion 2 — 100% cross-tenant coverage, generated

- The registry covers **every** public function: 198 total, **163 record-scoped**
  → a generated foreign-organization case each, 35 with no record argument → no
  tenant boundary to cross (structural coverage, asserted by the registry test).
- Running the suite: `✓ tests/unit/cross-tenant.generated.test.ts (165 tests)`.
- The suite is a real detector, not a rubber stamp: while this ticket was being
  written it failed on **two** genuine gaps, both now fixed — `buildChat.ts`
  (`planSite` / `generateSite` / `editPage` loaded a build and never checked the
  owning project; `editPage` had no ownership check at all) and
  `sellAI.generateDescription` (authenticated with `requireActionUser` and never
  authorized `args.projectId`, so a foreign caller could spend another tenant's
  AI budget).

## Security and privacy notes

- Tenancy is unchanged in kind, only in rule: **active membership of the owning
  organization**, with the pre-T2.1 owner fallback. Nothing widened: a foreign
  caller's error is still `Not found`, so a function can never confirm that a
  foreign id exists.
- No public function was added, so no allow-list entry was needed or added.
- The generated suite asserts *absence* of effect (row counts per table plus the
  returned value), which is what makes "returns nothing and writes nothing"
  checkable rather than asserted in prose.
- Notably **not** changed here: AI actions still take a client-supplied project
  snapshot (R4 / T0.4) — T2.2 authorizes the project id they are called with, it
  does not yet load that context server-side. `ModelGateway` (T2.9) owns that.

## Not in scope (deliberately)

- **T2.3's capability registry** — the builders resolve membership; they do not
  yet require a capability for a module action.
- `requireOrganization` / `requireOrgRole` keep T2.1's shape.
- The storefront's public read path (STATUS §5 item 3) still requires ownership:
  it needs T2.15's separate origin, not a widened guard.
