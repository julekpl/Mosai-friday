# T2.5 — Data registry, unified export and deletion, finalizer job

`[N][R]` · size **L** · **Status: done** (22 September 2026) · depends on T2.1
(T2.2–T2.4 also done)

## Why

The seed registry from T2.1 (`src/convex/lib/dataRegistry.ts`) describes only
the 14 tables T2.1 and T2.4 added; the other **40 of the schema's 54 tables**
are known to nobody but the hand-written `PROJECT_TABLES` list inside
`dal.cascadeDeleteProject`. AGENTS.md rule 12 says a deletion path must never
carry a hard-coded table list — and that CI must fail when a new
project-scoped table is unregistered. Neither is true yet: a new table can be
added and silently never exported, never retention-checked and never deleted.
Two more holes ride on the same seam:

- `billing.requestAccountDeletion` writes `users.deletionRequestedAt` and
  **nothing ever finalizes it** — the grace-period promise is a no-op.
- There is **no export path at all** (G9-style data-subject export) and no way
  for an operator or a customer to inspect *what* MOSAI holds, how it is
  retained and how it is deleted (the obligations inspector).

> **Reference docs:** the T2.5 row in `docs/pack/10-build-backlog.md` cites
> gates **G4** and **G9**; `docs/pack/04-adrs.md`, `docs/pack/08-module-contracts.md`
> and `MOSAI_CODE_PRODUCT_BLUEPRINT_V2.md` are — like in T2.1–T2.4 — **not
> present in this working tree**. This ticket was therefore scoped from the
> self-contained backlog row (*"Register every table; one deletion engine
> replacing both cascades (start from `dal.cascadeDeleteProject`); grace-period
> finalizer cron; obligations inspector interface"*, acceptance *"R10 passes
> with the full schema; CI fails on unregistered tables"*) plus `AGENTS.md`
> §5 rules 5/6/12/13 and §6. If G4/G9 land with extra requirements, the seams
> below (one registry, one engine, one cron, one inspector query) are where
> they attach.

## Owner decisions (asked before writing deletion code, `AGENTS.md` §7)

This ticket deletes data, so the four questions were put to the owner first
(recorded 22 September 2026):

| # | Question | Options | Decision |
|---|---|---|---|
| 1 | Should the grace-period finalizer actually delete, or only report? | active after grace · report-only · omit | **Active after grace** — the cron permanently finalizes accounts whose deletion request is older than the grace period, through the one shared engine. It only ever fires on an explicit user request. |
| 2 | How long is the grace period? | 30 · 14 · 7 days | **30 days** (`ACCOUNT_DELETION_GRACE_DAYS = 30`). |
| 3 | What happens when a paid subscription is still active at finalization? | skip + report · cancel at Stripe then delete · delete anyway | **Skip + report** — the account is not deleted, a `deletionBlockedReason` is recorded and shown in the pending-deletions report; no external write is made. |
| 4 | What happens to organizations the account owns? | solely-owned only · keep all · delete all owned | **Solely-owned orgs only** — an org with any other active member survives (only the deleting user's own membership rows go); a personal/sole-owner org is deleted with its memberships, invitations and agency links. |

Consequence: the shared account engine *refuses* (returns an honest blocked
result) whenever a to-be-deleted organization still has an active, trialing or
`past_due` subscription — for the immediate `billing.deleteAccount` path too,
which previously orphaned a live Stripe subscription silently.

## Do — what was built

### 1. The unified data registry — `src/convex/lib/dataRegistry.ts`

Every one of the schema's **54 tables** is registered (no hard-coded list
anywhere else). Each entry declares:

- `scope` (`project | organization | user | global`) and `tenantField`;
- `authorization` — which guard enforces reads/writes on the row;
- `export` (`included | excluded`) — credentials (`socialCredentials`,
  `adsCredentials`), OAuth state, platform/audit/billing-ledger tables and
  third-party identities (pending `invitations`) are **excluded**, so an export
  can never leak a token or another person's data;
- `retention` — the T2.1 vocabulary, unchanged;
- `deletion` — per-trigger rules `{ project?, account?, organization? }`, each
  one of:
  - `{ kind: "index", scans: [{index, field}] }` — rows reachable through a
    named index (the engine never guesses an index name);
  - `{ kind: "index-by-email", index, field }` — account deletion keyed by the
    user's email (`invitations.by_email`);
  - `{ kind: "parent", parentTable, parentIndex, childIndex, childField }` —
    children with no tenant index (`contentDocs`, `buildMessages`,
    `buildVersions`, `productMedia`), reached through their parent, the pattern
    R10 already proved;
  - `{ kind: "project-cascade", index, field }` — `projects` on account
    deletion: each matched project goes through the **full** project cascade;
  - `{ kind: "sole-owner", index, field }` — `organizations`: deleted only when
    no *other* active membership exists (owner decision #4);
  - `{ kind: "subject" }` — the tenant row itself, deleted last;
  - `{ kind: "none", reason }` — a documented, justified skip
    (`oauthStates`, `roles`, `adminAuditLog`, `billingEvents`, …).

The registry stays declarative and dependency-free: the tests, the audit
script and the engine all read it.

### 2. The one deletion engine — `src/convex/lib/dataLifecycle.ts` (new, internal)

Registry-driven; it contains **no table list of its own**:

- `deleteProjectData(ctx, projectId)` — parent-reached children first, storage
  blobs (`projectFiles.storageId`) before their rows, then every index scan,
  then the project row. `dal.cascadeDeleteProject` keeps its name and its two
  callers (`projects.remove`, account deletion) and now **delegates** here, so
  rule 12 is satisfied by construction.
- `deleteAccountData(ctx, userId)` — the ONE account path, used by both the
  immediate `billing.deleteAccount` and the finalizer:
  1. blocked-state check: if any organization the user solely owns has an
     active/trialing/`past_due` subscription → **return blocked, delete
     nothing** (owner decision #3);
  2. each owned project through the full project cascade;
  3. the user's own `memberships` (`by_user`);
  4. solely-owned `organizations` (`sole-owner`) with their memberships,
     invitations, agency links, billing customer and subscription mirror rows
     (owner decision #4) — `billingReceipts` / `billingInvoices` /
     `billingEvents` / `adminAuditLog` are **kept**: they are money and audit
     records (documented in the registry, dangling ids and all);
  5. pending `invitations` addressed to the user's email, the user's
     `platformAdmins` grant rows (the trail lives in `adminAuditLog`);
  6. the `users` row last.

### 3. Export — same registry, same reachability

`collectProjectExport` / `collectAccountExport` (in `lib/dataLifecycle.ts`)
walk the registry's `export: "included"` entries with the *same* index/parent
rules the deletion engine uses, so what you can delete is exactly what you can
export, and what is excluded (tokens, state rows, ledgers) is listed by name in
the result — `excluded: string[]`, never silently omitted. Public wrappers:
`data.exportProject` (org-scoped, `access.requireProject`) and
`data.exportAccount` (self-scoped, `access.requireUser`). Storage bytes are not
in the JSON (file metadata is); that is stated in the result.

### 4. The obligations inspector — `data.obligations`

One org-scoped query: the **full registry** (scope, authorization, export,
retention, deletion rules per table) plus, when a `projectId` is authorized,
live row counts per project-scoped table and the deletion/export status of the
project. `data.pendingDeletions` (platform-operator only) is the finalizer's
report side: every user with an open deletion request, its age against the
30-day grace and either `ready`, `waiting` or `blocked` + reason.

### 5. The grace-period finalizer — cron + internal mutation (owner decisions #1–#3)

- Schema (additive): `users.by_deletion_requested`
  (`["deletionRequestedAt"]`) and optional `users.deletionBlockedReason`.
  **Rollback:** delete the index line and the field; no data migration in
  either direction (Convex tolerates the stale index entries/field).
- `internal.data.finalizeAccountDeletions` (batch of 5 per run, so a long sweep
  never becomes one long mutation — the job framework is T2.6): requests older
  than `ACCOUNT_DELETION_GRACE_DAYS = 30` are finalized through
  `deleteAccountData`; rows without a request are filtered out explicitly
  (a Convex range over an optional field also matches documents that lack it);
  blocked accounts get `deletionBlockedReason` set (cleared when unblocked or
  canceled); each completed finalization writes one `adminAuditLog` row with
  the requesting user's id as `actorId` — *they* asked for it.
- `crons.ts`: `account-deletion-finalizer`, every 12 hours.

### 6. The CI gate — `scripts/audit-data-registry.mjs` (`bun run audit:data-registry`)

Parses `src/convex/schema.ts` from the working tree, imports the real registry
and **fails (exit 1)** when:

1. a schema table is **unregistered** (the row's acceptance criterion);
2. a registry entry names a table the schema does not declare (stale);
3. a table with a `projectId` field is not `scope: "project"` (or vice versa),
   outside the justified `oauthStates` exemption — which must itself justify a
   `none` deletion rule and lack a `by_project` index;
4. a deletion rule references an index, parent table or field the schema does
   not declare (the `buildVersions` bug, caught at CI time instead of at
   deletion time);
5. a `*Credentials*` table (or `oauthStates`) is marked `export: "included"`.

Wired into `bun run check` and the CI `security` job, right after the two
existing audits. Neither `audit:functions` nor `audit:capabilities` nor the
3-entry allow-list is touched.

### 7. File classification (T2.3 registry, extended as designed)

`CONVEX_FILE_OWNERS` gains `data: "base"` and `lib/dataLifecycle: "internal"`,
so `bun run audit:capabilities` classifies the new files (a library file that
exported a public function would fail it).

## Do not

- Hard-code a table list anywhere (rule 12) — extend the registry.
- Re-litigate or weaken T2.2–T2.4: no change to `audit:functions`,
  `audit:capabilities` semantics, or `scripts/public-functions-allowlist.json`
  (stays at 3).
- Write `paid`, `succeeded`, `connected`-style states; the finalizer writes
  only `deletionBlockedReason` and honest deletion itself.
- Delete money or audit records (`billingReceipts`, `billingInvoices`,
  `billingEvents`, `adminAuditLog`, `reconciliationRuns`) — registry says
  `kept-until-revoked`.
- Edit `.env` files (no keys are needed for this ticket).
- Add UI pages — the inspector is the query interface; the admin panel surface
  belongs to a later ticket.
