# T1.4 — Zero lint errors

`[R]` · size **M** · **Status: not started**

## Why

The pack measured **79 errors and 25 warnings** at baseline `da87ab7` (51 unused
variables, 17 `any`, 11 React-hook rules; worst files `convex/storefront.ts`,
`main.tsx`, `ContentEditor.tsx`, `PageEditor.tsx`, `Overview.tsx`). The tree has
changed since, so the first job is to re-measure, not to trust that number.

## Do

1. Run `bun run lint` and record the exact current error and warning counts in
   this file. That recorded number is the baseline for the ticket.
2. Fix the errors. Categorise them as you go so the PR is reviewable:
   - **Unused variables/imports** — delete them. If a value is genuinely
     impossible to consume yet, use it or drop it; do not prefix with `_` to
     silence the rule unless the parameter is part of a required signature.
   - **`any`** — replace with the real type from `_generated/dataModel` or a
     local type. Where the code is deliberately dynamic (`dal.ts` cascade), keep
     the documented eslint-disable and leave it alone.
   - **React-hook rules** — these are runtime bugs, not style. Fix the dependency
     arrays and the conditional/loop hook calls properly; read the rule's message
     and the surrounding component before changing anything.
3. Do not add `eslint-disable` for a whole file, and do not weaken
   `eslint.config.js`.

## Acceptance

- `eslint .` reports zero errors.
- Zero new `eslint-disable` directives beyond the ones already documented in the
  source (count them before and after, and report both).
- The warning count is recorded and either zero or each remaining warning is
  justified in the ticket file.

## Proof to record in the PR

Before/after `eslint .` summaries, plus the disable-directive counts before and
after.

## Note for whoever picks this up

This ticket is intentionally boring and mechanical, but it is a prerequisite for
T1.5: a CI job that fails on lint is worthless if the baseline is 79 errors,
because everyone learns to ignore it.
