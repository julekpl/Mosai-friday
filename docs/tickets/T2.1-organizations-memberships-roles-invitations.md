# T2.1 — Organizations, memberships, roles and invitations

`[N][M]` · size **M** · **Status: done** (22 September 2026) · depends on G-P1

## Why

Tenancy is owner-based (`projects.ownerId === user`). That cannot express a
business with teammates, an agency managing several clients, or a role that may
invite but not delete. T2.1 introduces the organization as the tenant above the
project and moves every existing project under its owner's personal
organization, without changing what a solo user sees.

This ticket is the data and authorization foundation. The function builders and
the generated cross-tenant suite are **T2.2** and are deliberately not started
here — `guards.requireProject` stays owner-based, so T2.1 only adds
organizations on top of today's tenancy.

> **Reference docs:** `docs/pack/08-module-contracts.md`, `04-adrs.md` (ADR-2) and
> `MOSAI_CODE_PRODUCT_BLUEPRINT_V2.md` are cited by the pack but are **not
> present in this working tree**. T2.1 was scoped from the self-contained T2.1
> row in `docs/pack/10-build-backlog.md` plus `AGENTS.md` (§5 rule 12, §6). If
> ADR-2's org-scoping shape differs, the guard seams (`requireOrganization`,
> `requireOrgRole`) are the only new contract and are easy to re-point.

## Do — what was built

1. **Schema** (`src/convex/schema.ts`), all additive:
   - `organizations` — `kind` (`personal` | `business` | `agency`), `ownerId`,
     `personalFor` (unique per user, via `by_personal_for`).
   - `memberships` — `(organizationId, userId)`, `role`, `status`
     (`active` | `invited` | `suspended`), `by_organization_user`.
   - `invitations` — normalized `email`, `role`, single-use server-generated
     `token`, `by_token`.
   - `roles` — the seeded role registry (key, rank, capabilities).
   - `agencyClientLinks` — `agencyId`/`clientId`/`status`; revoked, never
     deleted.
   - `projects.organizationId` (optional) + `by_organization`, so the migration
     can backfill and new projects are written with their org.
2. **Role model** (`src/convex/lib/roles.ts`): one canonical
   `ROLE_CAPABILITIES` map (`owner` ⊃ `admin` ⊃ `member`), `ROLE_RANK` and
   `roleCan`. The `roles` table is seeded from it, guards enforce from it, tests
   assert against it.
3. **Authorization** (`src/convex/guards.ts`): `membershipFor`,
   `requireOrganization` (throws `Not found` for a foreign org or a non-member —
   never confirms a foreign id) and `requireOrgRole(capability)`. Every new
   public function is guarded by one of these.
4. **Module** (`src/convex/organizations.ts`): create/list/get/members,
   personal-org resolution (`getOrCreatePersonalOrganization`), invitations
   (`invite`, `invitations`, `acceptInvitation`, `revokeInvitation`), role and
   membership administration (`updateMemberRole`, `removeMember`, `leave`) and
   agency links (`linkAgencyClient`, `unlinkAgencyClient`, `agencyClients`).
5. **Last-owner protection**: `assertNotLastOwner` refuses to remove or demote
   the only active owner; the sole owner must stay (personal orgs cannot be left
   at all).
6. **Idempotent migration**
   (`organizations.migrateProjectsToPersonalOrganizations`, an
   `internalMutation`): seeds the role registry, creates one personal
   organization per user through the `by_personal_for` index, and patches only
   projects whose `organizationId` is unset. A second run reports zero.
7. **`projects.create`** now writes `organizationId` from the owner's personal
   organization (idempotent).
8. **Registry** (`src/convex/lib/dataRegistry.ts`): each new table's scope,
   tenancy field, authorization, export and retention policy. This is the T2.1
   seed that T2.5 replaces with the full data registry, unified export/deletion
   and the grace-period finalizer.

## Acceptance — evidence

### Acceptance criterion 1 — existing projects appear under a personal organization

`tests/unit/organizations.test.ts`:

```
✓ moves every pre-organization project into its owner's personal organization, idempotently
✓ creates a new project under the owner's personal organization
✓ ensurePersonal is idempotent and returns the same organization
```

The first seeds two projects directly (owner set, no `organizationId`), runs
`internal.organizations.migrateProjectsToPersonalOrganizations`, and asserts a
`personal` organization exists per owner with an `owner`/`active` membership and
that each project's `organizationId` points at its own owner's org; a second run
reports `{ organizationsCreated: 0, projectsAssigned: 0 }` and creates no extra
org.

### Acceptance criterion 2 — roles are enforced

```
✓ seeds the role registry from the canonical definitions
✓ a member cannot invite, remove or change roles, and cannot read a foreign org
✓ an admin can invite members but cannot grant ownership or remove an owner
✓ an owner can promote a member, and the last owner cannot be demoted or removed
✓ links and revokes agency client organizations, and rejects a non-agency or a non-client caller
```

A member gets `does not allow`; a non-member gets `Not found` on `get`; an admin
may invite `member` but not `owner` and may not remove the owner; the sole owner
cannot be demoted (`at least one owner`), cannot remove themselves (`leave`),
and cannot leave (`at least one owner`); a promoted member can.

## Known limitations recorded honestly

- **No UI ships with T2.1.** The acceptance criteria are data and authorization;
  organization switching, member management and invite screens are a later
  slice. The functions return machine-readable ids (including the invite token)
  so a UI can be built without changing the server contract.
- **No email is sent.** There is no `EmailGateway` yet (T0.8), so `invite`
  **returns the token to the inviter** and never claims a send. No `sent`
  state exists.
- **Agency links need the caller to administer both sides.** Until the E3.9
  client-consent handshake exists, an agency can only link a client org it also
  administers — an agency cannot silently attach an arbitrary tenant. This is
  the safe interpretation, not the finished product flow.
- **`guards.requireProject` is still owner-based.** Members of an organization
  other than its owner cannot open the owner's projects yet; wiring org-membership
  into every project function is T2.2 (org-scoped builders + the generated
  cross-tenant suite). T2.1 deliberately does not touch that surface.
- **Account deletion does not yet cascade organizations/memberships.** The
  registry records the retention policy; the unified deletion engine and
  finalizer are T2.5. `billing.deleteAccount` is unchanged here to avoid mixing
  a migration with a deletion-behavior change.
- **Migration is invoked, not scheduled.** It is an `internalMutation`.
  Auto-running long work belongs to the job framework (T2.6); running it per
  deployment is documented and idempotent.
