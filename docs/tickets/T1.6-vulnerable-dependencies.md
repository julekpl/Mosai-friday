`[R]` · size **S** · **Status: done** (22 September 2026) · depends on T1.1

## Why

The pack's production audit at baseline `da87ab7` reported **1 high
(`react-router`) and 1 moderate (`hono`)**. Re-audited as instructed — **both
were stale**: `react-router` resolves to 7.18.4 and `hono` to 4.13.8, and neither
is flagged by `bun audit` on this tree. The real exposure is two transitive
packages the pack never named: `@auth/core` (via `@convex-dev/auth`) and
`undici` (via `cheerio` / `@vly-ai/integrations`). The dependency-audit leg of
the T1.5 CI `security` job was staged `continue-on-error` specifically until this
ticket; it is now a hard failure.

## Findings with no in-range fix

**`undici@5.29.0` — GHSA-vrm6-8vpv-qv8q, GHSA-v9p9-hfj2-hcw8, GHSA-vxpw-j846-p89q
(high) + 7 moderate + 2 low.** Every advisory is fixed at `undici >= 6.23.0`;
undici 5.x is end-of-life and has no 5.x backport. The declared chain is

```
@vly-ai/integrations@0.6.14  (latest published: 0.6.14)
  └─ ai@^5.0.0 → ai@5.0.262  (latest 5.x; pins @ai-sdk/provider-utils 3.0.37)
       └─ @ai-sdk/gateway@2.0.154
            └─ @ai-sdk/provider-utils@3.0.37  (latest 3.0.x; requires undici ^5.29.0)
```

so **no upgrade inside the declared ranges can clear it.** Clearing it in-range
would require `ai@6/7`, which `@vly-ai/integrations` cannot use (it is written
against the `ai` v5 API) and which the pack defers to T2.9 (retire
`@vly-ai/integrations`). `@vly-ai/integrations` is imported by five `"use node"`
Convex actions (`ai.ts`, `buildChat.ts`, `social/copilot.ts`, `buildPlan.ts`,
`sellAI.ts`), so the code path is live.

**Fix applied:** a root `overrides` entry forcing `undici` to `^7.19.0`.

```json
"overrides": { "undici": "^7.19.0" }
```

*Compensating control / why this is safe.* `^7.19.0` is the exact range
`cheerio` already declared, so the override only rewrites the one
`@ai-sdk/provider-utils` edge (5 → 7) and de-duplicates the tree to a **single**
`undici` (7.29.1) — no second major, and nothing currently working is downgraded.
`@ai-sdk/provider-utils` consumes exactly two `undici` exports, via
`createRequire(...)("undici")` — `Agent` (constructed as
`new Agent({ connect: { lookup } })`) and `fetch` (called with a `dispatcher`
init). Both are present and signature-compatible in undici 7; the package's
`undici` usage is a Node-only fetch wrapper, and the whole package is scheduled
for removal in T2.9. The override is a deliberate, recorded exception to the
declared range, and it is the only such override in the repo.

### Why `@convex-dev/auth@0.0.94` and not the latest `0.0.95`

The upstream changelog is decisive:

- **0.0.94** — "chore: bump `@auth/core` peer dependency" — moves the peer from
  `^0.37.0` to `^0.41.1`, which is what lets `@auth/core@0.41.3` (the critical
  fix) resolve at all. Nothing else changes.
- **0.0.95** — additionally changes OTP sign-in failure semantics: `signIn`
  called with only a `code` now *resolves* with `{ tokens: null }` instead of
  *rejecting*. `src/pages/Auth.tsx` relies on `signIn` rejecting to show
  "The verification code you entered is incorrect.", so 0.0.95 is a behaviour
  change this ticket does not need.

`0.0.94` is therefore the smallest bump that clears the advisory, and it avoids
an unrelated, untested sign-in behaviour change. `@auth/core` is also added as an
explicit direct dependency (`^0.41.3`): it is a peer of `@convex-dev/auth`, and
without it bun kept the previously resolved 0.37.4 and warned
`incorrect peer dependency "@auth/core@0.37.4"`.

### Routes and the auth page (the ticket's `react-router` concern)

`bun run test:e2e` passed all four journeys after the upgrade, including
`marketing and auth smoke › the landing page renders and routes to sign-in`,
which mounts the lazy `/auth` route — i.e. `BrowserRouter` resolution and the

### OAuth callbacks (the ticket's `hono` concern)

`hono` is not used by the HTTP layer, and never was: `src/convex/http.ts` builds
its router with `httpRouter` from `convex/server`. `hono` is a declared direct
dependency that nothing in `src/` imports (`rg 'from "hono"' src/` → no matches);
it is left in place because removing it is out of T1.6's scope and it is not
flagged. The callbacks were exercised directly against the dev deployment
(`convex dev --once` deployed them):

```
GET https://adjoining-gnat-502.convex.site/api/social/callback → 302
  location: .../app?error=missing%20code%20or%20state
GET https://adjoining-gnat-502.convex.site/api/ads/callback    → 302
  location: .../app?error=missing%20code%20or%20state
```

Both routes are registered and execute their handler (correctly rejecting a
request with no `code`/`state`), so the Convex HTTP layer is intact. HTTP routes
are served on the `.convex.site` origin, not `.convex.cloud`.

### Secret gate still live

The T1.5 ticket quoted a literal dummy `x-api-key` value in its proof table. The
`vly-email-otp-key` rule correctly matched it, so `bun run check` and the CI
`gitleaks` job were red on this tree before this ticket. The doc line was
redacted (`a temp file with a dummy x-api-key value (16+ characters)`) rather
than allow-listing `docs/tickets/`, which would have weakened the scanner over a
whole directory. The rule was then re-proven live: a planted dummy value in a
temp file failed the scan, and the tree passed again once it was removed.

## Known limitations recorded honestly

- **The `undici` override violates a declared range by design.**
  `@ai-sdk/provider-utils@3.0.37` asks for `^5.29.0`; the override forces 7.x.
  Bun supports only a single-level scoped override and 1.3.14 rejects the nested
  object / `parent>child` / `resolutions` path forms with a warning, so a flat
  `overrides` entry is the only mechanism available on the pinned toolchain. The
  override disappears when T2.9 retires `@vly-ai/integrations`, and T2.9 should
  remove it then.
- **The local managed dev server had to be worked around for the e2e run.** The
  clean `rm -rf node_modules` reinstall deleted Vite's pre-bundled dependency
  cache out from under the already-running dev server, which then served
  `504 Outdated Optimize Dep` for `input-otp` and never re-optimized. The
  journeys were therefore run the way CI runs them — Playwright starting its own
  server — and all four passed. The previously running server is a stale-cache
  artifact of the reinstall, not a code or type defect.
- **The codegen CI job still needs `CONVEX_DEPLOY_KEY`** (T1.5's dated TODO,
  unchanged and out of scope here).
