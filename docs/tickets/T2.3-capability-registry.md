# T2.3 — Capability registry and per-add-on entitlements

`[R][M]` · size **L** · **Status: done** (22 September 2026) · depends on T2.1 (builds on T2.2)

## Why

T2.2 made the **organization** the tenant in the authorization path. It did not
answer the next question: *is this caller entitled to this module at all?* The
answer lived in four places that could disagree, and mostly did:

- `PLAN_MODULES` in `billing.ts` — one tier→module list, read by the UI;
- hard-coded module arrays in `AppShell.tsx`, `App.tsx` (the route gate) and
  `Billing.tsx` (the plan cards) — three copies of the same list;
- a per-module `assertModule("sell")` call, which only two modules had;
- **nothing else.** `builds.create`, `cms.publishPage`, `products.create`,
  `posts.create`, `insights.create` and every other add-on function were
  reachable straight from the client on the `free` plan; the sidebar lock was the
  only thing standing in the way, and a sidebar is not a gate.

On top of that, every plan check read `user.plan` of **whoever called**. In an
organization that is the wrong plan twice over: a teammate with a personal `free`
account was locked out of the add-ons the organization paid for, and a personal
`scale` account unlocked a `free` organization's modules.

T2.3 makes capabilities **one canonical, typed registry** and wires every
module function to enforce it — server-side, before the handler runs, for
queries, mutations, actions *and* the cron job.

> **Reference docs:** the T2.3 row in `docs/pack/10-build-backlog.md` cites
> `docs/pack/08-module-contracts.md` and `04-adrs.md`, which are **not present in
> this working tree** (the same gap T2.1 and T2.2 recorded). T2.3 was therefore
> scoped from the self-contained backlog row — *"Replace tier `PLAN_MODULES` and
> `AppShell` locks; capability states per blueprint §3; country matrix stub"* with
> the acceptance *"Enabling or disabling an add-on changes routes, queries,
> mutations, actions and jobs consistently"* — plus `AGENTS.md` §5 rules 2/5/10/12
> and §6. The registry's shape (`{module}.{action}`, the four states, the country
> stub) is the one seam to re-point if `08`/`04` land differently.

## Do — what was built

### 1. The registry — `src/convex/lib/capabilities.ts` (new)

One dependency-free module (only `lib/roles.ts`) that everything else derives
from. It is importable by the Convex functions, the audit script and the UI
types, so a module list cannot exist anywhere else:

| Export | What it is |
|---|---|
| `MODULE_IDS` / `MODULE_DEFINITIONS` | the eight add-ons, their labels and the **actions each one defines** |
| `CAPABILITIES` / `capabilityKey` / `parseCapability` | the capability vocabulary: `<module>.<action>`, `view · edit · manage · publish · spend` (34 keys). A key outside the registry is refused, never silently allowed — `sell.spend` does not exist, so it cannot be granted |
| `PLAN_MODULES` / `modulesForPlan` / `planIncludesModule` | plan × module. `billing.ts` re-exports `PLAN_MODULES`, so the old import sites keep working — there is one list |
| `ROLE_MODULE_ACTIONS` / `roleAllows` | role × action **inside** a module (member: view+edit; admin: +manage+publish; owner: +spend). `lib/roles.ts` stays the organization-administration map |
| `resolveCapabilityState` | plan + role + country + setup → `included \| locked \| needs_setup \| unavailable` (blueprint §3) |
| `capabilityMessage` | the user-facing text for a non-`included` state — one place, so the server and the UI say the same thing (the plan message is byte-identical to what `assertModule` always threw) |
| `COUNTRY_MATRIX` / `countryPolicy` | **stub**: one wildcard policy, no country-specific legal claim. The seam exists; the matrix is blocked on the owner's answer (`STATUS.md` §6 #4) |
| `capabilityMatrix` | the resolved per-module/action matrix the UI renders |
| `CONVEX_FILE_OWNERS` | which convex file belongs to which module (`module \| base \| service \| internal`) — the audit's map |
| `CAPABILITY_EXEMPTIONS` | the four documented exceptions, each with a reason the audit enforces is non-empty |

`assertModule` is **gone** entirely: a plan was always only half of a capability.

### 2. Enforcement — `src/convex/guards.ts`

- `projectTenant` / `projectCapability` / `organizationCapability` resolve a
  capability for a record: **the organization's plan × the caller's role**, with
  the owner fallback only for a pre-T2.1 project. `planForOrganization` uses the
  organization **owner's** plan — deliberately not the caller's.
- `moduleQuery` / `moduleMutation` / `moduleAction` (new builders) declare a
  module, and:
  - a **write** enforces the capability from its record argument (`projectId`, or
    any row id resolved to its owning project) **before the handler runs** — a
    lacking caller cannot touch a row, let alone write one;
  - a **read** gets an `OrgAccess` whose authorizations (`ownedProject`,
    `ownedRow`, `requireProject`, `requireOrganization`, `requireCapability`,
    `capabilityState`) enforce the capability, so a locked module reads nothing
    and a foreign organization still sees `Not found`;
  - an **action** does the same through the action-safe probes
    (`capabilityStateForAction`, `recordProjectForAction`). `moduleAction` works
    in a `"use node"` file (verified against the real deployment), so the Node AI
    actions are gated by the same builder as everything else.
- `capabilityStateForProject` (internal) resolves a capability for a **job**: a
  cron has no user, so the axis is the tenant's plan, with the tenant's own
  authority (the role was checked when the user scheduled the work).

**149 module functions in 31 convex files** now go through `moduleQuery` /
`moduleMutation` / `moduleAction` (was: 2 modules checking a plan, everything
else checking nothing):

|---|---|---|

| Journeys | `journeys` | 5 / 5 |

Plus the job gate in `social/executor.ts`: a due post whose project no longer
includes `promote.publish` is **not published**; the post records the honest
reason (`Not published — Your current plan does not include "promote"…`) and
carries no receipt, instead of slipping out through the queue.

### 4. The read side for the UI — `src/convex/entitlements.ts` (new)

`entitlements.matrix` (the resolved plan × role matrix for a project — `null`
for a caller who cannot reach it), `entitlements.plans` (the plan cards, from the
registry) and `entitlements.vocabulary` (the capability vocabulary). The UI never
hard-codes a tier.

### 5. Routes and locks read the same resolution

- `src/hooks/use-module-entitlements.ts` (new) — one hook over
  `entitlements.matrix`, with the plan list as the fallback before a project is
  selected.
- `AppShell` sidebar, the `App.tsx` module route gate and the `Overview` module
  cards now render that resolution (and label the honest state — `upgrade`,
  `needs setup`, `unavailable`), so the route, the nav, the queries and the
  mutations change together when an add-on is enabled or disabled.
- `Billing.tsx` no longer carries per-plan module arrays: the cards read
  `entitlements.plans`. Prices stay in the UI until T2.4 owns billing.

### 6. The gate — `scripts/audit-module-capabilities.mjs` (new)

`bun run audit:capabilities`, wired into `bun run check` and the CI `security`
job. Driven entirely by the registry, it fails when:

1. a convex file is **unclassified** (a new file cannot quietly escape),
2. an `internal` file exports a public function,
3. a module function is declared with anything but
   `moduleQuery`/`moduleMutation`/`moduleAction` naming its own module,
4. the declaration does not enforce: no record argument *and* no
   capability-aware `access.*` call (in a `"use node"` file: no record argument
   and no `requireActionCapability`),
5. an exemption has no reason, or is **stale** (no such function any more).

Nothing in the gate can be silenced by adding an allow-list entry: the only
documented path is an exemption in the registry with a reason, and the T0.6
allow-list stays at **3 entries**.

## Acceptance — evidence

### Acceptance criterion — enabling or disabling an add-on changes routes, queries, mutations, actions **and jobs**, consistently

**Queries and mutations.** `tests/unit/entitlements.test.ts` (26 tests) is
generated over the registry, not written per module:

| Generated axis | Cases | What it proves |
|---|---|---|
| reads, per module × plan | 8 × 4 | rows appear exactly when `planIncludesModule(plan, module)` — the same table, the same seeded row, hidden on a downgrade and visible again on an upgrade, and never deleted |
| writes, per module | 8 | on `free`, the module's own create mutation is refused with the registry's message and **writes nothing**; for the three free modules it succeeds |
| role × action | 1 | a real organization: the member can draft an ad change (`promote.edit`) and is refused the approval (`promote.spend`) with *"Your role in this organization does not allow that action."*; the owner's approval succeeds and the row leaves `draft` |
| actions | 1 | `entitlements.matrix` / `plans` agree with the registry for every plan |
| jobs | 2 | the scheduled-post worker refuses to publish for a plan without `promote` (status `failed`, the entitlement reason, **no receipt**, and it tries again honestly once the credential is the only thing missing), and it resolves the organization's plan, not a user's |

**Routes.** `App.tsx`'s module gate and `AppShell`'s locks both read
`entitlements.matrix` (the server's resolution), so a disabled add-on is not
reachable by URL and is not offered in the sidebar; `Overview` and `Billing`
render the same registry data. `bun run test:e2e` / `test:a11y` stay green
(13 + 5).

**Three defects found and pinned as regressions**

1. **Nothing enforced the entitlement server-side.** A `free` plan could call
   `builds.create` (and 140 other module mutations) from the client.
   *Regression:* "refuses a plan-locked module mutation with the registry's
   message" — the write is refused, no row is written, the read renders empty,
   and after an upgrade the same project's write and read agree.
2. **The plan came from the caller, not the organization.** *Regression:*
   "resolves the plan from the organization, not from the caller's own account"
   — both directions: a teammate whose personal plan is `free` succeeds on the
   organization's `growth` add-on; a teammate whose personal plan is `scale` is
   still refused on a `free` organization's `build`.
3. **`entitlements.matrix` returned a populated envelope to a foreign caller**
   instead of nothing — found by the T2.2 **generated** cross-tenant suite the
   moment the new function existed (`entitlements:matrix returned tenant data to
   a foreign-organization caller`). It now returns `null`, and that generated
   case is green.

## Security and privacy notes

- Tenancy is unchanged (T2.2's rule). The capability layer is **additive**: it
  can only narrow what a caller reaches, never widen it.
- Nothing about a locked module is simulated and nothing claims success: a locked
  read returns nothing, a locked write throws the registry's message, and the job
  that cannot publish records `failed` with the reason and no receipt.
- A capability key outside the registry is refused (`parseCapability`), so a typo
  cannot grant access.
- `entitlements.matrix` returns `null` — not an empty envelope — for a caller who
  cannot reach the project, so a foreign caller learns nothing about it.
- The country matrix is an explicit **stub**: no country-specific legal or
  regulatory claim is modelled. That needs the owner (money/tax/legal — `AGENTS.md`
  §7), tracked as `STATUS.md` §6 #4.
- No public function was added to the T0.6 allow-list; no exemption was added to
  silence a failure — the four exemptions are pre-existing AI/admin settings with
  no tenant to resolve, and the audit now fails on a **stale** exemption.

## Not in scope (deliberately)

- **Stripe** (T2.4): prices, checkout, webhooks, dunning, reconciliation. This
  ticket makes the *entitlement* consistent; it does not touch payment.
- **`ModelGateway`** (T2.9): the AI actions are capability-gated but still take a
  client-supplied project snapshot (R4 / T0.4 remainder).
- **`ApprovalGate`** (T2.12) and step-up auth (T2.8): the approval is a
  capability check, not yet an approval record.
- The per-country matrix and any legal wording.
